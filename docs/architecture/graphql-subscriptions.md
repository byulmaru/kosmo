# GraphQL subscriptions

GraphQL Yoga sends subscriptions to clients over Server-Sent Events (SSE). Shared event delivery uses Yoga's typed `createPubSub` contract with the process-wide `redisEventTarget` from `@kosmo/core/redis/pubsub`.

The shared API Yoga plugin wraps every authenticated async GraphQL subscription result. Session and Profile end signals therefore close any matching stream; the Home timeline below is one consumer of this common lifecycle.

Each local consumer creates its typed `createPubSub<Topics>({ eventTarget: redisEventTarget })` instance. The shared module lazily initializes one Redis publisher and one subscriber from `REDIS_URL` on first use; importing it does not connect. If `REDIS_URL` is unset, it does not connect or fall back to localhost. Return each subscription iterator when its consumer finishes to remove that consumer's topic listener. The worker closes the shared connections from its existing `finally` cleanup path.

The worker publishes `homeTimelinePostAdded` to the topic scoped to the recipient Profile after either of the two Home insertion paths creates a new entry. The event payload contains only `postId`. The API exposes nullable `Subscription.timeline: TimelineEvent`; `TimelineEvent` currently has one member, `TimelinePostAdded`, whose nullable `post` field contains the actual Post when it resolves. The subscription uses the operation's selected Profile to choose the same Home topic and authorizes at start with the same Member permission used for Home. On each event, the API resets Pothos's context cache before resolving the current Post while preserving the operation's trusted context fields. This prevents the long-lived SSE operation from reusing stale related Profile, PostContent, or Media records; ordinary current Post visibility and lifecycle checks run, and `TimelinePostAdded.post` can be `null` when the Post cannot be resolved. The Redis event payload still contains only `postId`; it does not carry a Post snapshot or bypass those checks.

The API captures the authenticated Session for each operation when the subscription starts. After current Session revocation commits, the API mutation and web BFF invoke the core post-commit effect. Its existing Redis command client waits a bounded time for readiness, then publishes one Yoga-compatible `sessionEnded:<sessionId>` message with the typed `true` sentinel. The API wraps the subscription result so a matching Session end signal completes that SSE operation normally, without a GraphQL error, and cleans up both the source and signal iterators. It does not recheck Session state for each Post event; start authorization and the current Post visibility and lifecycle checks remain in effect. Other Session IDs do not match, so their streams are unaffected.

After a successful Profile disable, including an idempotent retry, the core service best-effort publishes one Yoga-compatible `profileDisabled:<profileId>` message with the same typed `true` sentinel. The API captures the selected Profile when the subscription starts. A matching Profile signal completes that SSE operation normally and cleans up the source and all signal iterators, even when the operation uses another Session. A Profile signal leaves subscriptions for other Profiles on the same Session running, and it does not revoke the Session. A Session-only subscription listens only for Session end.

The client subscribes to the actual Post and prepends it to the already loaded Home connection; it does not refetch the full Home list for each event. Since Redis delivery can be missed, a latest Home read on app resume or subscription reconnection reconciles gaps. If the reader is below the newest position, the client keeps the reading position and defers lifecycle revalidation until it returns to the top. `새 글 보기` scrolls there immediately without a per-event query; a pending lifecycle revalidation runs after reaching the top.

When logout replaces the actor Environment, the client disposes its current SSE subscription operation.

Redis Pub/Sub is transient, and every GraphQL subscription built on this foundation tolerates event loss. A publish issued while the publisher is disconnected is dropped and is not queued for later delivery. Subscribers reconnect and restore their active topic listeners, but messages published while disconnected are not replayed. The transport does not provide persistence, event IDs, cursors, or replay. The Home timeline reconciles possible gaps with a latest read on app resume or subscription reconnection.

Session end uses this same transient delivery path: a missed logout signal is not replayed, so an already-open operation that misses it may remain open. A newly created operation authenticates again at subscription start and is subject to the normal revoked-Session check.

Profile disable uses the same transient delivery limit: a missed signal is not replayed, so an already-open operation that misses it may remain open. A newly created operation must pass the normal selected Profile authorization and lifecycle checks.

For Home timeline events, recipient eligibility and direct Post/PostContent reads continue to apply the current viewer Profile and Instance visibility checks. Missing the close signal does not preserve access to Followers Only content after Profile disable.

Topic names and payload tuples follow Yoga's `createPubSub` behavior, including dynamic topics encoded as `<topic>:<id>`. Event details cross Redis as JSON, so payloads must be JSON serializable. No-payload events are represented in the serialized envelope without changing their `detail` value.
