# 멀티 프로필 진단 지표 계약 검토 기록

## 상태와 승인 범위

- 작성일: 2026-08-31
- 담당 이슈: [PROD-555](https://linear.app/byulmaru/issue/PROD-555)
- 상태: Domain Gate 검토안. 아래 계산 규칙은 아직 승인되지 않았다.
- 이 기록은 검토 이력이며 canonical 정책이나 OpenSpec 구현 근거가 아니다. 승인한 규칙은 별도의
  `docs/domain/policies/multi-profile-usage.md`에 반영한다.

사용자는 Codex 작업 `PROD-555 Spec`에서 PROD-520의 취소 상태를 유지하고 PROD-555가 멀티 프로필 지표의
정의까지 맡는 방향에 “진행”이라고 답했다. 지표 정의 소유권은 확정됐지만, 이 답을 아래 계산 규칙 전체의
승인으로 해석하지 않는다. PROD-520에 남은 2026-07-29 초안도 승인된 계약으로 사용하지 않는다.

## 근거와 기존 책임

- [Account](../objects/account.md)는 로그인과 Profile Membership의 기준이며, 기본 소셜 행동 주체는
  [Profile](../objects/profile.md)이다.
- [Account-Profile Membership](../objects/account-profile-membership.md)은 Account와 Profile의 실제 역할
  관계다. Profile을 여러 개 보유한다는 사실과 여러 Profile을 사용했다는 사실은 다르다.
- [ADR 0019](../decisions/0019-selected-profile-authorization-boundary.md)는 선택 Profile의 자격을 Membership과
  조회 가능 상태로 판단한다. 현재 Local 화면이라는 이유로 Remote Profile을 분석 정의에서 임의로 제외하지 않는다.
- [PROD-520](https://linear.app/byulmaru/issue/PROD-520)의 2026-07-29 댓글은 주간 활성 Account, 서울 시간 주차,
  서로 다른 Profile 2개 이상, 생성·선택·핵심 행동 지표의 출발점이다. 승인 전 초안이라는 상태는 유지한다.
- [PROD-819](https://linear.app/byulmaru/issue/PROD-819)는 Web 분석 실행 환경과 typed custom event를,
  [PROD-795](https://linear.app/byulmaru/issue/PROD-795)는 개인정보·운영 통합 검증을 소유한다.
- 기본 분석 전환의 production acceptance와 archive는 [PROD-575](https://linear.app/byulmaru/issue/PROD-575)가
  계속 맡는다. PROD-555의 metric 검증을 기본 분석 전환의 완료 증거로 대신하지 않는다.

## 계산 규칙 검토안

아래 R1–R7은 하나의 검토안이다. 실제 이벤트 이름·property shape·Insight query는 이 규칙을 승인한 뒤
OpenSpec에서 정밀화한다. 제품 객체의 조회 권한, Profile 선택 동작과 UI는 바꾸지 않는다.

### R1. 관측 대상과 기간

- production Web에서 수집된 관측만 사용한다. 이벤트가 발생한 시점에 인증 Account를 확인할 수 있어야 한다.
- 나중에 로그인한 익명 방문을 인증 활동으로 소급하지 않는다.
- 주차는 Asia/Seoul 기준 월요일 00:00 이상, 다음 월요일 00:00 미만이다.
- 관측이 발생한 시각으로 주차를 정한다. 일요일에 발생해 월요일에 수신한 관측은 일요일이 속한 주에 넣는다.
- 진행 중인 주는 부분 집계라고 표시한다. 초기 비교는 완료된 주끼리 한다.
- 완료 주도 조회 시점까지 수신된 관측으로 다시 계산한다. 지연 수신으로 이전 수치가 달라질 수 있으며,
  완료 주라는 표시는 수치를 고정했다는 뜻이 아니다. 결과에는 집계 실행 시각을 표시한다.
- 같은 Account가 여러 Session·기기를 사용해도 Account 수는 한 번만 센다.
- SDK 차단·전송 실패로 수집하지 못한 활동을 추정하거나 완전 수집이라고 주장하지 않는다.

### R2. 주간 활성 Account

해당 주에 인증된 화면 조회 또는 포함된 앱 제품 행동이 한 번 이상 관측된 Account를 주간 활성 Account로
센다. 이하 WAA라고 부른다. 선택 Profile이 없는 Account도 이 조건을 만족하면 분모에 포함한다.
여기서 정의하는 WAA는 이 멀티 프로필 지표의 분모다. 다른 진단 지표나 북극성 지표의 공통 분모까지
자동으로 확정하는 것은 아니다.

포함하는 앱 행동은 Profile 생성·선택 성공, Post 생성 성공, Follow 실행 성공, 검색 제출·결과 로드·결과
선택이다. 자동 클릭 수집, replay, pageleave, performance, feature flag와 SDK 진단 이벤트만으로는 WAA가 되지
않는다. 실패한 요청만 있고 포함된 관측이 하나도 없는 경우에도 WAA로 세지 않는다.

### R3. 멀티 프로필 활성 사용률

Account별로 다음 중 하나가 확인된 Profile을 그 주에 사용한 Profile로 센다.

- 인증된 화면 조회 시점에 선택되어 있던 Profile
- 선택을 성공적으로 마친 Profile
- Post 생성 또는 Follow 실행을 성공한 행동 주체 Profile

같은 Account·Profile 조합은 그 주에 한 번만 센다. Profile을 생성했다는 사실만으로 사용했다고 보지 않으며,
생성 후 선택 성공이나 화면 조회·핵심 행동이 별도로 확인되어야 한다. 보유 Profile 수와도 구분한다.

멀티 프로필 활성 Account는 사용한 Profile이 서로 다른 2개 이상인 WAA다.

```text
멀티 프로필 활성 사용률
= 멀티 프로필 활성 Account 수 / WAA × 100
```

분모가 0이면 0% 대신 계산할 수 없음으로 표시한다. 동일 Profile을 여러 Account가 사용한 경우에도 각각의
Account 안에서 사용 여부를 판단한다. 다른 Account의 활동을 가져와 2개 조건을 채우지 않는다.

### R4. 생성과 전환 빈도

Profile 생성 횟수는 생성이 실제로 성공한 횟수다. 생성 후 자동 선택이 실패해도 생성 성공은 유지한다.

Profile 전환은 이미 선택한 Profile이 있는 상태에서 사용자가 다른 기존 Profile을 선택하고 성공한 경우다.
다음은 전환 횟수에서 제외한다.

- 같은 Profile 재선택
- 선택 Profile이 없을 때의 최초 선택
- 새 Profile 생성 직후의 자동 선택
- Session 복원·화면 재조회
- 취소되거나 실패한 선택

이 제외는 분석 분류이며 기존 Profile 선택 동작을 막거나 바꾸는 요구사항이 아니다. 생성 후 자동 선택도
성공했다면 R3의 사용 Profile에는 포함할 수 있다.

주간 생성·전환 총횟수를 각각 표시한다. 전환 보조 지표는 해당 주 멀티 프로필 활성 Account가 수행한 전환
총횟수를 그 Account 수로 나눈 값이다. 그 집단 안의 전환 0회 Account도 분모에 포함하며, 집단이 비어 있으면
계산할 수 없음으로 표시한다. 생성 빈도는 주간 생성 총횟수와 생성한 distinct Account 수를 함께 표시한다.

### R5. Profile별 핵심 행동과 중복

초기 핵심 행동은 Post 생성과 Follow 실행 성공이다. Follow 실행 결과가 즉시 관계 성립인지 요청 생성인지는
분리해서 표시한다. 요청 생성만으로 관계가 성립했다고 해석하지 않는다.

행동은 그 행동을 수행한 Profile에 귀속한다. 결과를 수집할 때 화면의 선택 Profile이 바뀌었더라도 다른
Profile로 옮기지 않는다. Account도 원래 행동을 수행한 인증 주체에 귀속한다. 처리 도중 Account가 바뀌거나
로그아웃돼도 다음 Account의 행동으로 기록하지 않는다. 원래 주체를 확정할 수 없는 관측은 임의 귀속하지 않는다.
타인의 Profile을 방문하거나 Follow 대상으로 선택한 사실은 그 Profile을 사용한
증거가 아니다.

Account 수는 Account 단위로, 사용 Profile 수는 Account·Profile 조합으로 중복 제거한다. 같은 성공 관측의
재전송은 한 번만 세고, 사용자가 별도로 성공한 행동은 각각 센다. transport 재전송과 독립 행동을 같은 시각이나
같은 Profile이라는 이유만으로 합치지 않는다.

재게시·반응·북마크 전용 지표와 후속 행동 추가는 이번 초기 핵심 행동 집합에서 제외한다. 다른 이슈의 향후
이벤트를 이번 지표의 필수 전제로 삼지 않는다.

### R6. 제외 대상과 개인정보

- 익명 관측과 development·test 환경은 제외한다.
- 내부·테스트 Account와 알려진 봇·자동화 Account는 관리된 제외 목록으로 제외한다.
- 제외 목록의 관리와 정기 점검은 PROD-555 담당자 정혜주가 맡는 안을 제안한다.
- 모든 지표는 같은 제외 목록 버전을 적용한다. 결과에는 관측 기간과 계산 규칙·제외 목록 버전을 남겨
  같은 관측 집합을 같은 규칙으로 계산했는지 대조할 수 있게 한다.
- 일반 조회와 주간 비교에는 조회 시점의 최신 제외 목록을 과거 주에도 동일하게 적용한다. 새로 등록한 테스트
  Account의 과거 활동도 제외하므로 이전 수치가 바뀔 수 있다. 이전 보고 수치와 비교할 때는 양쪽의 집계 시각과
  제외 목록 버전을 함께 확인한다. 변경된 결과를 과거에도 같은 값이었다고 제시하지 않는다.
- Account 제외는 해당 Account의 모든 활동에 적용한다. 같은 Profile을 사용하는 다른 Account까지 함께
  제외하지 않는다.
- 알려지지 않은 봇을 모두 식별했다고 주장하지 않는다. 이름·handle·IP 주소로 새로운 추정 규칙을 만들지 않는다.
- 분석에는 opaque Account 식별자와 행동 주체 또는 선택 Profile 식별자를 사용한다. 이름·handle·본문·검색
  원문과 다른 사람의 대상 Profile 식별자를 이 지표 때문에 추가로 수집하지 않는다.
- 실제 Account 제외 목록은 접근이 제한된 운영 설정에서 관리하고 저장소 문서에 복제하지 않는다.

### R7. 검증과 운영 책임

- PROD-555는 이 metric의 canonical 계약, 이벤트 변경, 초기 Insight·dashboard, 합성 데이터 대조 및
  실제 수집 데이터의 계약 대조를 함께 맡는 안을 제안한다.
- PROD-555가 소유한 모든 결과와 검증을 마친 뒤 해당 metric change의 delta spec 동기화·archive도
  PROD-555가 맡는다. 기존 분석 전환 change의 archive는 맡지 않는다.
- PROD-795의 통합 검증 의존성은 유지한다. metric 논의·설계 착수와 production 수집 인수 완료는 구분한다.
- 초기 운영 점검은 담당자가 매주 완료된 직전 주의 결과와 제외 목록을 확인하는 안을 제안한다.
- 과거 OpenPanel 이벤트와의 호환·이관은 제외한다. 새 계산 계약으로 확인할 수 있는 관측 시작점을 남긴다.

## 합성 집계 예시

다음은 검토용 가상 데이터이며 운영 수치가 아니다. 모두 같은 완료 주에 발생했고, A–D는 제외 대상이 아니다.

| Account             | 관측                                             | 사용 Profile 수 | 전환 횟수 | 생성 횟수 |
| ------------------- | ------------------------------------------------ | --------------- | --------- | --------- |
| A                   | P1으로 화면 조회, 사용자가 P2로 전환 성공        | 2               | 1         | 0         |
| B                   | P3으로 화면 조회, 같은 P3 재선택 성공            | 1               | 0         | 0         |
| C                   | 첫 P4 생성 뒤 자동 선택 성공                     | 1               | 0         | 1         |
| D                   | P6으로 화면 조회, P5 생성 성공 뒤 자동 선택 실패 | 1               | 0         | 1         |
| 내부 테스트 Account | 여러 Profile로 활동                              | 제외            | 제외      | 제외      |

이 예시에서 WAA는 4, 멀티 프로필 활성 Account는 1, 사용률은 25%다. 주간 생성은 2회, 생성한 Account는
2개다. 전환은 1회이며, 멀티 프로필 활성 Account당 평균 전환은 1회다.

다음 경계도 승인 후 검증 대상에 포함한다.

- 주 시작 직전·정각, 다음 주 시작 정각
- 같은 Account의 여러 기기와 같은 Profile의 여러 Account
- 로그인 전 관측과 로그인 후 관측, Account 교체
- Profile 정보가 없는 화면 조회: WAA에는 포함할 수 있지만 Profile 수를 추정하지 않음
- 동일 관측 재전송과 독립적으로 성공한 두 행동
- 분모 0, Profile 생성 성공 뒤 선택 실패, 모든 활동이 제외된 주
- 일요일 발생·월요일 수신 관측, 완료 주 재집계, 새 제외 Account의 과거 활동 제거
- 두 Profile로 화면을 조회했지만 수동 전환은 없는 Account: 사용 Profile 2개, 전환 0회로 평균 분모에 포함
- 출발 Profile의 사용 관측 없이 전환 도착 Profile만 관측된 Account: 총 전환에는 포함하지만 다른 사용 증거가
  없으면 멀티 프로필 집단에는 포함하지 않음

## 대안과 감수할 결과

| 쟁점                | 검토안                                 | 대안과 차이                                                                                        |
| ------------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 사용 Profile의 기준 | 화면 조회·선택 성공·핵심 행동          | Post·Follow만 세면 구현은 단순하지만 읽기 중심 Profile 사용을 놓친다.                              |
| 전환의 기준         | 사용자가 다른 기존 Profile로 바꾼 성공 | 모든 선택 성공을 세면 현재 이벤트를 바로 활용할 수 있지만 재선택·생성 자동 선택도 전환으로 잡힌다. |
| 핵심 행동           | Post 생성·Follow 실행, 결과 구분       | 다른 행동까지 포함하면 별도 이슈와 계측 의존성이 늘어난다.                                         |
| 내부·자동화 제외    | 버전이 있는 운영 제외 목록             | 임의 추정은 줄지만 목록에 없는 자동화 Account는 남을 수 있다.                                      |

검토안은 읽기 중심의 Profile 사용을 포함하는 대신, 인증된 화면 조회에 선택 Profile이 정확히 연결되는지
검증할 필요가 있다. 기존 선택 이벤트만 세는 것보다 전환 의미를 정확히 구분하지만, 성공 원인의 구별을
추가로 계측해야 한다. 이벤트·속성 형태는 아직 결정하지 않았다.

3. PROD-555 본문에 canonical 참조와 구현·검증·archive 책임을 정렬해 Issue Gate를 확인한다.
4. 그 뒤 OpenSpec의 proposal, specs, design, decisions, tasks를 작성·윤문·검증한다.
5. Spec Gate 승인 뒤 구현은 별도 세션에서 시작한다. 이 기록 자체를 gate 승인으로 사용하지 않는다.

## 2026-09-03 검토 결과

사용자 정혜주는 Codex 작업 `PROD-555 Spec`에서 R1–R7 설명을 검토한 뒤, WAA를 단독 분모로 쓰면
단일 Profile Account의 증가와 기능 채택 변화를 구분하기 어렵다고 지적했다. 이에 다음처럼 지표를 나눴다.

- 멀티 Profile 활성 사용률은 사용 가능 Profile이 같은 시점에 2개 이상이었던 WAA를 분모로 삼는다.
- WAA를 분모로 한 기존 비율은 멀티 Profile 도달률로 이름을 바꾸고 보조 지표로 둔다.
- 기능 리텐션과 대상 Account 제품 리텐션은 주간 비율과 분리해 W+1, W+4로 확인한다.
- WAA, 멀티 Profile 대상 WAA, 멀티 Profile 활성 Account의 절대 수도 함께 본다.

정혜주는 이 수정안을 포함한 설명에 “스펙 승인”이라고 답했다. 이 답으로 R1, R2, R4–R7과 위에서 고친
R3을 함께 승인했다. 승인된 현재 정책은 [Multi-Profile Usage Policy](../policies/multi-profile-usage.md)에
반영했다. 이 기록의 기존 R3과 합성 예시는 승인 전에 검토한 안을 보존한 것이므로 현재 계산식으로 사용하지
않는다.
