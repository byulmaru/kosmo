# Manual remote Post recovery

Use the registered `remotePostLookupWorkflow` to fetch and materialize one remote ActivityPub Note by its canonical HTTP(S) object URI. A Worker must be polling the `kosmo` task queue in the selected Temporal namespace.

## Start a lookup

With the Temporal CLI configured for the target namespace, start a Workflow with the Note's own `id` URI:

```sh
temporal workflow start \
  --type remotePostLookupWorkflow \
  --task-queue kosmo \
  --input '{"objectUri":"https://remote.example/notes/123"}'
```

The CLI returns the Workflow ID. Read its result with:

```sh
temporal workflow result --workflow-id YourWorkflowId
```

Replace `YourWorkflowId` with the ID returned by `start`. In Temporal Web, start the same Workflow type on task queue `kosmo` and provide the same JSON input. The Workflow ID can be generated by Temporal for a standalone lookup.

The input may include `signingProfileId` when the remote server requires an authenticated request:

```json
{
  "objectUri": "https://remote.example/notes/123",
  "signingProfileId": "<active-local-profile-uuid>"
}
```

The ID must identify an active local Profile on the configured active local Instance. A Follow relationship is not required. If omitted, the lookup uses the configured local context without selecting a Profile signer. A Featured sync passes the selected follower Profile and the remaining shared document budget to the same child Workflow automatically.

A standalone lookup uses a 2 MiB parsed-document budget. Featured syncs count collection pages and each Note against the same cumulative budget.

## Interpret the result

- `created` means the Note was materialized as a Post. The result includes its Post ID, author Profile ID, and parsed-document byte count.
- `duplicate` means the Note already maps to a Post. The result returns that Post and its stored owner without creating another one.
- `rejected` means the fetched object or Note did not pass the existing materialization checks. The result includes a reason such as an invalid Note or exceeded document budget.

The Workflow uses the existing remote Note materializer. A signing Profile authenticates retrieval only; it does not authorize a `DIRECT` Note. A `DIRECT` Note still requires an eligible local Mention. The standalone lookup does not replace a Profile's Featured pins, run a bulk import, expose a new API or UI, or apply remote Post Updates.

The lookup can only materialize a Note the remote server currently serves. A deleted, invalid, or unavailable Note cannot be reconstructed by this operation; transient request failures may retry before the Workflow fails. During a Featured sync, an earlier child may already have materialized its Note if a later child fails, while the previous Featured pin snapshot remains until the full sync succeeds.

The CLI options are documented in the [Temporal Workflow command reference](https://docs.temporal.io/cli/command-reference/workflow).
